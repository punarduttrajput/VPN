## To close on a Linux host (one command)

All remaining Linux-only checks are automated in
[scripts/verify-linux.sh](scripts/verify-linux.sh) — it runs both peers in network
namespaces on a single box (no second machine needed):

```sh
sudo ./scripts/verify-linux.sh   # needs root, iproute2, iperf3
```

It verifies, with PASS/FAIL output and a non-zero exit on failure:
- **M3** — real TUN `ferrum0` comes up in each namespace; clean teardown on signal (FR1).
- **M5** — `ping` succeeds across the encrypted tunnel both directions.
- **M6/NFR1** — link shaped to 1 Gbps; tunnel throughput ratio reported (hard gate only with `STRICT_THROUGHPUT=1`).
- **M6/NFR2** — added latency < 2 ms vs. baseline (ping).

### NFR1 throughput — an honest status

Measured on CI with the underlay shaped to a realistic 1 Gbps link
(`tc netem rate 1000mbit`):

| Host | Baseline Mbps | Tunnel Mbps | Ratio |
|---|---|---|---|
| Shared CI (2-vCPU) — single serialized loop (old) | 956 | 356 | 0.37 |
| Shared CI (2-vCPU) — pipelined data plane | 956 | 493 | 0.52 |
| **Real Linux kernel (WSL2, 2026-06-22), run A** | 312 | 293 | **0.94** ✅ |
| **Real Linux kernel (WSL2, 2026-06-22), run B (`STRICT_THROUGHPUT=1`)** | 319 | 242 | **0.76** ✅ |
| NFR1 target | — | — | 0.70 |

**The NFR1 ratio passes the strict hard gate on a real Linux kernel** — a
`STRICT_THROUGHPUT=1` run reports **9/9 PASS** including `tunnel throughput
>= 0.70 x link`. The earlier 0.52 was a *shared-runner artifact*, not a data-plane
limit: on a 2-vCPU GitHub runner the high 956 Mbps baseline outruns a single
userspace tunnel, depressing the ratio. On WSL2 the tunnel tracks the underlay
closely — which is what NFR1 actually measures. This confirms the long-standing
hypothesis that the data plane (not the cipher or the loop structure) was never
the problem; the shared runner was.

The observed ratio **varies run-to-run (0.76–0.94)** because the WSL2 host is
CPU-bound and noisy; both ends of that range clear 0.70, but the margin is not
large — so the honest claim is "the ratio gate passes on real Linux," not a fixed
0.94.

Honest caveat: the WSL2 host is itself CPU/NIC-bound (~312 Mbps baseline, well
below a true 1 Gbps link), so the 1000 Mbit `tc` shaping wasn't the binding
constraint. The **ratio** NFR is met; **absolute line-rate** at a genuine 1 Gbps
link on dedicated hardware is still unconfirmed.

Remaining levers (for absolute line-rate, not the ratio):
- **✅ Pipelined data plane (done)** — overlaps I/O with crypto across cores.
- **✅ UDP GSO/GRO batching (done)** — amortizes per-packet syscall cost on both paths.
  `sendmmsg` + **UDP GSO (`UDP_SEGMENT`) send path** (`UdpTransport::send_batch` coalesces a
  leading run of equal-sized datagrams into one `sendmsg`); and now **UDP GRO (`UDP_GRO`)
  receive path** — the socket enables GRO, one `recvmsg` returns a coalesced run, and
  `recv`/`try_recv` drain it segment-by-segment (`GroBuffer`) with no further syscalls.
- **eBPF/XDP fast path** (Phase 6) for line-rate forwarding.

To enforce the 70% gate on dedicated/representative hardware:
`sudo STRICT_THROUGHPUT=1 ./scripts/verify-linux.sh`.

> The re-handshake recovery requirement (NFR5) is now covered by an in-process
> unit test and no longer needs a host to verify.

- 2026-07-19 — **Security hardening M1: fail-closed coordinator auth + token/cert↔key binding (SEC-001, SEC-002).** A 2026-07-19 security review found the coordinator's `authenticate()` silently returned `Ok(None)` (self-declared ACL tags trusted) whenever OIDC was off or unconfigured — a wide-open-mesh-by-default posture — and that even with OIDC on, a verified token wasn't bound to the presented WireGuard public key, so a leaked/replayed token could register an attacker-chosen key under its tags. **SEC-001** (`ferrum-coordinator` binary): authentication is now the default. A new `ferrum_coordinator::resolve_auth_mode(oidc_configured, insecure_no_auth)` — pure, unit-tested, called once at the top of `main()` before the registry/listeners start — fails fast unless OIDC is configured *or* the operator passes the new `--insecure-no-auth` flag (combining both is also rejected as a likely misconfiguration); the explicit opt-out logs a loud warning at startup and again every 5 minutes (`warn_insecure_periodically`). Enforced identically whether or not the crate is built with the `oidc` feature, so a non-OIDC build can't silently default to open either. **SEC-002** (`ferrum-coordinator` registry + service): `Registry` gained an `identity_keys` map (namespaced `oidc:<sub>` / `mtls:<cert fingerprint>` → public key, persisted under the `sqlite` feature via two new `Store::{load,upsert}_bindings` trait methods with default no-op impls for `MemoryStore`) plus `bind_identity`/`rebind_identity`: the first authenticated registration for an identity claims a key; a later registration with a *different* key — or for a key another identity already claims — is rejected `FailedPrecondition`; the authorized path to move a key is the existing `rotate_key` RPC, which now also enforces the caller's identity actually owns the key it's rotating away from (closing a related gap: `rotate_key` previously trusted *any* valid token to rotate *any* device's key). - 2026-09-24 — **Security hardening M2: relay register challenge + rate limits (SEC-003).** The relay bound `key -> source addr` on any bare `Register` frame, so anyone who knew a peer's (public) key could redirect its relayed traffic, and spoofed sources made it a reflector. A mapping now changes only after a one-round-trip challenge (new `crates/transport/src/relay_auth.rs`): `Register` → `Challenge(relay_x25519_pub, cookie)` → `Response(key, cookie, proof)` from the same source. The **cookie** is a stateless keyed-BLAKE2s MAC over (30 s epoch, source addr, key) — proves return routability, costs the relay no memory per spoofed source. The **proof** is a keyed-BLAKE2s MAC under `X25519(client_priv, relay_pub)` — proves possession of the key's private half, which the ticket's nonce echo alone wouldn't (an attacker using their own real address could still claim someone else's key); low-order keys are rejected. Same primitives as WireGuard's own cookies. The register frame is padded to 65 bytes so the 49-byte challenge never amplifies; a keepalive for the already-live mapping stays a silent refresh (no challenge, no rate cost). Token-bucket limits: per source IP (burst 32, 8/s) on challenges + proof checks — the proof's X25519 is also gated behind the cheap cookie check — and per key (burst 4, 1 per 5 s) on *verified* mapping changes only, so a third party can't drain a victim's budget; tables are bounded (65 536 keys, idle buckets swept). Draining relays don't even challenge unknown keys. New aggregate metrics: `ferrum_relay_register_challenges_total`, `ferrum_relay_registers_rate_limited_total`, `ferrum_relay_register_proofs_rejected_total`. Client side: `RelayMeshTransport::connect` now takes the node's `StaticSecret` and completes the round-trip before returning (bounded at 500 ms — so the mesh's first WireGuard handshake over the relay isn't dropped; an unreachable relay costs that wait, not an error), and `recv_from` answers any later challenge (relay restart, NAT rebind). `client-core`'s `connect_relay` passes the device key; the XDP harness (`examples/relay_traffic.rs`) uses fixed test private keys and the new public `relay::register_via`. XDP is unaffected — it only fast-paths `Data` frames for committed mappings, and the hook still fires only on commit. **Wire-incompatible**: relays and clients must be upgraded together. Tests: 7 `relay_auth` unit tests (honest proof verifies, cookie bound to source + key, cookie expiry, wrong-private-key proof rejected, low-order keys rejected, rate-limiter burst/refill, bounded table) and 5 new `RelayServer` tests (a bare register creates no mapping and the spoofer receives nothing, a hijack with a real cookie but the wrong private key is rejected and B's mapping survives, a replayed cookie from another address is rejected, a 200-register flood is throttled at the burst, per-key roam limit), plus the existing relay/drain/XDP-hook tests and the tunnel's two relay mesh tests migrated to real keys. `cargo test --workspace` + `--features ferrum-cli/masque` green; `cargo fmt --all --check` and `cargo clippy --all-targets -D warnings` clean across default/quic/masque/`real-tun,helper-ipc` (on this Windows host; the Linux `xdp` build is left to CI). - 2026-09-24 — **Security hardening M2: outer-transport cert pinning, part 1 (SEC-004).** QUIC/MASQUE used `SkipServerVerification` (accept any cert), so the outer camouflage layer had zero server authentication — payloads stayed WireGuard-safe, but an on-path box could terminate the QUIC/HTTP-3 layer for metadata, probing, or downgrade.
